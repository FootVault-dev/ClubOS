# Agent Notes — warehouse

> **Durable memory across loop runs.** Read every run; append what you learn. Keep it tight.

## How to build / test this project

- Install:    `npm install` (should already be done; if `node_modules` is missing, run it)
- Typecheck:  `npm run check`   ← the ALWAYS gate — must be clean before marking any task done
- Build:      `npm run build`   ← run additionally for any task touching `client/`
- Logic tests: plain assertion scripts `script/test-warehouse-*.ts`, run via `npx tsx script/test-warehouse-<x>.ts` (exit 0 = pass). **No vitest/jest in this repo — do not add a test framework.**
- 🔴 **There is NO database in this environment** — no `.env`, no `DATABASE_URL`, no local Postgres. Never open a DB connection. `script/apply-warehouse.ts` and `script/seed-warehouse.ts` are WRITTEN here but only ever RUN by a human later. Logic tests must be DB-free: inject a fake `tx`/db object that records calls.

## Conventions (house rules — violations have caused prod incidents)

- **Schema:** all new tables in `shared/schema.ts`, prefix `wh_`, copy the Drizzle patterns of the existing `shop_*` tables (same pk/timestamp/index helpers). Migration = ONE new file `migrations/2026-07-13_warehouse.sql`, additive only, `CREATE TABLE IF NOT EXISTS` / `CREATE [UNIQUE] INDEX IF NOT EXISTS`.
- **`script/apply-warehouse.ts`:** copy the newest existing `script/apply-*.ts` dry-run pattern (BEGIN → run migration → verify every table via `to_regclass` + every index via `pg_indexes`, assert partial indexes contain `WHERE` → ROLLBACK unless `--apply`). List EVERY new table and index in its verification arrays.
- **NO CHECK constraints on enum-ish text columns** (movement_type, reason_code, status…) — validate in `shared/warehouse.ts`. (A stale CHECK once 500'd the MFL checkout.) CHECKs only for true invariants (`delta <> 0`, non-negative money).
- **Derived, never stored:** `available` (= on_hand − active reservations), loan `overdue` (= due_on < today ∧ status='out'), PO `qty_received` (= Σ receipt movements). Do not add columns for these.
- **The ledger is append-only** — no UPDATE/DELETE code paths on `wh_movements`, ever. Stock corrections are new adjustment movements.
- **Atomic stock guard:** all cache updates go through `postMovementGroup` (SPEC §4.2) in one transaction with the ledger insert. Non-negative enforcement: a conditional `UPDATE … SET on_hand = on_hand + $delta WHERE on_hand + $delta >= 0` (insert row first if absent); 0 rows updated → reject the whole transaction with "insufficient stock at <LOCATION>". Guard skipped only when the item has `allow_negative`.
- **Money in CENTS** (integer). Quantities `numeric(12,3)` (Drizzle `numeric` maps to string in TS — convert explicitly at the edges).
- **Dates:** NZ timezone; use the repo's existing `nzTodayIso()` helper (grep for it) — never `new Date().toISOString()` for a calendar date, never round-trip an ISO date string through `Date`.
- **Routes:** new files `server/warehouse-routes.ts` (HTTP) + `server/warehouse.ts` (movement engine) + `server/warehouse-sync.ts` (channel sync); register routes in `server/index.ts` next to the shop routes registration. Auth: `requireAuth` + `requireTab("warehouse")` from `server/auth.ts` (org comes from the `X-Workspace-Slug` header). Requisition SUBMIT + own-requisition views are `requireAuth` only (any staff).
- **Tabs/UI wiring** (exact checklist): `shared/tabs.ts` → add `{ slug: "warehouse", title: "Warehouse", url: "/admin/warehouse" }` to `printsTabs` AND `"warehouse"` to `SUPER_ADMIN_ONLY_TABS`; `client/src/components/app-sidebar.tsx` → `printsNav` entry; `client/src/App.tsx` → routes; pages in `client/src/pages/warehouse-*.tsx` matching the visual style of the existing `prints-*.tsx` pages (dark premium, TanStack Query via `@/lib/queryClient`).
- **Frontend:** no CDN scripts — npm deps only, pinned exact versions. Scanner: `barcode-detector` ponyfill package (ZXing-C++ WASM, self-hosted assets) + native fast-path feature-detected via `getSupportedFormats()` contents (never `'BarcodeDetector' in window`). QR generation: the `qrcode` npm package.
- **Shopify:** GraphQL only (SPEC §4.3 / D9) via a minimal fetch-based client in `server/warehouse-sync.ts`; env vars per store (`WH_SHOPIFY_CUFC_TOKEN`, `WH_SHOPIFY_SIU_TOKEN`, store domains) read lazily; every push carries an idempotency key; mark mutation syntax `// TODO-verify(live)` — a human verifies against current shopify.dev before deploy. All sync behaviour behind env flags so the code is inert without config.
- **Do not touch** other features' code except the ONE flagged edit in T13 (smallest possible diff in `server/shop-routes.ts`). Never modify `deploy.sh`, `.github/`, existing migrations, or `drizzle.config.*`.
- **Commits:** one per task, message `loop(warehouse): T<n> <summary>`.

## Lessons learned (append-only)

- **2026-07-22 — THE TYPECHECK GATE IS `bash script/check-warehouse-gate.sh`, NOT a clean `npm run check`.** The canonical-2 base carries ~545 pre-existing tsc errors (routes.ts/schema.ts/storage.ts — snapshotted per-file in `script/BASELINE-TSC.txt`), so "check must be clean" was never achievable and is why the first loop runs stalled. The gate script passes iff warehouse-owned files have ZERO errors and no file regresses past its baseline count. Wherever PLAN.md/SPEC.md say `npm run check`, run the gate script instead. `npm run build` DOES pass at baseline and remains a hard gate for client-touching tasks.
- 2026-07-22 — a crashed earlier run mangled `package-lock.json` (restored from base 541b58a) and left a PARTIAL `shared/warehouse.ts` (2 tsc errors, no test script). T1 must finish/fix it, not start over blindly.
- 2026-07-22 (T1) — `const X: ReadonlySet<SomeUnionType> = new Set([...string literals])` does NOT typecheck: `new Set([...])` infers `Set<string>` from the literal array, which isn't assignable to `ReadonlySet<SomeUnionType>`. Always give the type param explicitly: `new Set<SomeUnionType>([...])`. Same trap will bite any future `Set`/`Map` built from a literal array and assigned to a narrower-typed field (e.g. future `wh_*` enum sets in the engine or sync code).
- 2026-07-22 (T2) — **`createInsertSchema(table).omit({...})` throws a spurious tsc TS2322 "Type 'boolean' is not assignable to type 'never'" on ANY table whose `id` column uses `.generatedAlwaysAsIdentity()`** (drizzle-zod 0.7.0 + zod 3.24.2 + TS 5.6.3 inference bug — reproduced in isolation, confirmed unrelated to which/how-many keys are passed to `.omit()`, confirmed NOT triggered when the table uses `serial("id").primaryKey()` instead). This is already the majority of shared/schema.ts's 154 pre-existing baseline errors (~154 of ~160 total `.omit()` call sites) — it is a pre-existing, file-wide issue, not something introduced by warehouse code, and NOT something to mass-fix (out of scope, huge diff, forbidden by "don't touch other features' code"). **Fix for any NEW `wh_*` insert schema: drop `.omit(...)` entirely and just export `createInsertSchema(table)`.** This is behaviourally identical whenever every field you'd have omitted (id, createdAt, updatedAt, processedAt…) already carries a DB default — drizzle-zod already infers defaulted columns as optional on insert without needing `.omit()`. Verify with a throwaway `const x: InsertX = { requiredFieldOnly: ... }` compiling fine. Same trap will bite every future `wh_*` insert schema (routes/engine tasks) that copies the `.omit({id:true,...})` convention from elsewhere in schema.ts.
- 2026-07-22 (T2) — Drizzle's column-level `.unique()` (e.g. `sku: text("sku").notNull().unique()`) does NOT correspond to any predictable index name in the hand-written SQL migrations this repo uses (no drizzle-kit push/generate here — schema.ts and the raw `.sql` migration files are two independently-maintained layers). Don't rely on Postgres's implicit `<table>_<column>_key` auto-naming for anything an `apply-*.ts` script needs to verify by name — give every unique constraint an EXPLICIT `CREATE UNIQUE INDEX IF NOT EXISTS <name> ON ...` in the migration (even a single-column one), and keep Drizzle's `.unique()` in schema.ts purely as TS-side documentation (harmless, no DB effect either way).
- 2026-07-22 (T3) — `server/db.ts` THROWS at module-EVALUATION time if `DATABASE_URL` is unset (`if (!process.env.DATABASE_URL) throw new Error(...)`), not lazily on first use. Any module that does a plain VALUE import (`import { db } from "./db"`) at its top level will crash the instant it's loaded — including by a `tsx script/test-*.ts` run, which has no `.env` in this worktree. `server/accounting/post.ts` (found in the sibling `budget-automation` worktree) already solved this: `import type { db as realDb } from "./db"` for TYPES ONLY (erased at compile time, never executes anything) + a lazy `const { db } = await import("./db")` *inside* the function body, only reached when that specific function actually runs. Copied this exact pattern into `server/warehouse.ts` (`runMovementGroup`, `reconcileStock`'s default). Any future warehouse module (routes, sync) that needs the real `db` must follow the same shape — a stray top-level `import { db } from "./db"` anywhere in a file that a test script imports (even transitively) will take the whole test run down with "DATABASE_URL must be set", and the failure looks nothing like the real bug.
- 2026-07-22 (T3) — A generic `Pick<typeof realDb, "insert" | "select" | ...>` fake (the accounting-precedent style) only stays easy to fake when every DB call is a SIMPLE `.values(row).returning()`/`.onConflictDoNothing().returning()` whose fake can dispatch purely on the VALUES it's handed. The moment a query needs a COMPUTED conflict action (`onConflictDoUpdate` with a `sql\`col + ${delta}\`` SET/setWhere) or a multi-table aggregate (a FULL OUTER JOIN + GROUP BY for reconcile), a plain object-literal fake can no longer introspect what the real drizzle call would do — the `sql` template's internal AST isn't meant to be pattern-matched by test code. Don't fight this: define a small BESPOKE interface (`WarehouseDb`/`ReconcileDb` — a few named async methods expressing the actual operations, e.g. `upsertStockLeg`, `listStockVsLedger`) that a plain in-memory-Map fake can implement directly, and keep exactly ONE real adapter function (`warehouseDbFromTx`, `reconcileDbFromRealDb`) that's type-checked against the schema but deliberately never unit-tested (it needs a live Postgres — that's a human/deploy-time concern, not a loop-agent one). This is the natural evolution of the accounting pattern once the query gets past "trivial single insert", not a departure from it — keep using the `Pick<realDb,...>` style for anything that stays trivial.
- 2026-07-22 (T4) — A plain HTTP CRUD/routes file (no engine-style transaction logic, e.g. `warehouse-routes.ts`) does NOT need the lazy-`db`-import trick from T3's lesson — that trick exists only because `server/warehouse.ts` is imported by a DB-free `tsx script/test-*.ts` run. A routes file is never imported by a test script (there's nothing to unit-test in "call db.select().where(...)"), only ever loaded by the real running server (which always has `DATABASE_URL`), and tsc doesn't execute code — so a plain top-level `import { db } from "./db"` is fine and is what every existing standalone routes file (`feedback-routes.ts`, `market-research-routes.ts`, `club-dossier-routes.ts`) already does. Don't over-apply T3's lesson here.
- 2026-07-22 (T4) — AGENTS.md's "register in `server/index.ts` next to the shop routes registration" is slightly imprecise: `registerShopRoutes(app)` actually lives inside `server/routes.ts` (called from within `registerRoutes()`), not `index.ts`. The real, already-established pattern for a NEW standalone feature module in this codebase is the `registerFeedbackRoutes`/`registerMarketResearchRoutes`/`registerClubDossierRoutes` trio — a dynamic `await import(...)` + call, inside the async IIFE in `index.ts`, after `registerRoutes()` and before the cron-job registrations. Used that for `registerWarehouseRoutes` too; future warehouse route-group tasks (T6–T9) that add whole new registration functions (vs. extending this same file) should follow the identical spot, not go hunting for a literal "shop routes" line in `index.ts`.
- 2026-07-22 (T4) — Master-data CRUD (items/locations/aliases) intentionally does NOT use `postMovementGroup`/`server/warehouse.ts` at all — creating/editing/deleting an item, location or alias never touches `wh_movements`/`wh_stock`. Keep it that way: only stock-affecting flows (T5 reservations onward) call into the movement engine. If a future task finds itself importing `runMovementGroup` from a CRUD handler in `warehouse-routes.ts`, that's a sign the operation actually belongs in a different route group.
- 2026-07-22 (T4) — A `zone` field that's DERIVABLE from another field the user already types (here: a location's `zone` from its own `code`, per the schema comment "first segment of a bin code, or the named zone itself") should be computed server-side on every write and never accepted from the client, even as an optional override — same "derived, never stored [as independently-editable]" spirit as `available`/`overdue`/`qty_received` elsewhere in this spec, just applied to a plain data-integrity field rather than a stock number. Added `deriveLocationZone()` to `shared/warehouse.ts` rather than inlining the one-liner in the route, so T16's admin UI can show the same derivation for a live preview without duplicating it.
- 2026-07-22 (T5) — Postgres does NOT allow `FOR UPDATE` on a query with `GROUP BY`/aggregate functions — so a "computed multi-row aggregate that also needs to serialize concurrent callers via row locks" (here: `available(item) = Σ on_hand(sellable bins) − Σ active reservations`) can't be one aggregate query with a lock clause bolted on. The real adapter (`reservationDbFromTx.getAvailableForItem`, `server/warehouse.ts`) has to be TWO plain `SELECT ... FOR UPDATE` statements (no GROUP BY, just the raw rows) with the summing done in JS after. This is a variant of T3's "bespoke ReservationDb/WarehouseDb seam, not `Pick<typeof realDb,...>`" lesson, but the specific new wrinkle (FOR UPDATE + aggregate can't coexist) is worth its own line for the next SQL aggregate this spec needs under a lock (T9's chargeback report and T11's count variance are both aggregates, though neither needs row-locking the way a concurrent reserve/reserve race does).
- 2026-07-22 (T5) — When one function's real DB work spans TWO bespoke seams at once (`consumeReservation` needs both `WarehouseDb`, to post the movement, and `ReservationDb`, to flip the reservation's status, inside the SAME transaction), don't inline `{ ...warehouseDbFromTx(tx), ...reservationDbFromTx(tx) }` at every call site — TS will usually infer the spread's type fine, but it's a needless re-check every time and reads worse than a single named `combinedDbFromTx(tx): WarehouseDb & ReservationDb` helper with an explicit return-type annotation (forces the assignability check to happen exactly once, at the helper's definition). The two source interfaces must have zero overlapping method names for the spread to be safe — true here (`WarehouseDb`'s 3 methods vs `ReservationDb`'s 6 don't collide) but worth checking again if a future task adds a 3rd seam to the mix.
- 2026-07-22 (T5) — A reservation that is item-level, not (item, location)-level (per `wh_reservations`' actual schema — confirmed by reading it rather than assuming from the SPEC prose), means `consumeReservation` posting its movement at a SPECIFIC location can still hit `InsufficientStockError` even though the item-level `available` check inside `reserveStock` already passed — reserving against total item availability across every sellable bin can't know in advance which single bin a later dispatch scan will actually name. This is not a bug to "fix" by pre-checking the target bin inside `reserveStock` (the bin isn't even known yet at reserve time, e.g. a webhook-driven reservation from an order) — it's the correct, expected two-layer guard (item-level at reserve, location-level at consume), and T5's own test suite had to deliberately construct a "enough overall, not enough in THIS bin" fixture to exercise it (a naive single-bin fixture can't reach this path, since a first-ever `(item,location)` row always succeeds regardless of sign — see T3's lesson on that). Any future task adding a second consume-shaped flow (e.g. T9 requisition pick) should expect the same two-layer possibility and not assume "it was reserved, so consuming it will always succeed."
- 2026-07-22 (T6) — When a PLAN.md line's prose is genuinely ambiguous ("over/short/damaged → QUARANTINE leg + discrepancy note" could mean ALL THREE route to quarantine, or only damaged does while over/short are just noted), resolve the ambiguity against the nearest hard constraint rather than the more elaborate reading: D15's reason-code enum has exactly one code that applies at receiving time (`damaged`) — no `over_receipt`/`pending_review` code exists, and inventing one is out of scope for a single task (it's a taxonomy change, "don't invent taxonomy" per D15's own rationale). So only damaged stock is quarantined; over/short are compared against an `expectedQty` (defaulted from the line's derived outstanding qty) purely to build a note string on the movement group. Documented this reasoning inline in both `shared/warehouse.ts` and the route handler so a future task doesn't "fix" it into routing over-receipts to quarantine without first adding a reason code for it.
- 2026-07-22 (T6) — A derived multi-row total split by a discriminant column (here: `qty_received` per PO line, split into good vs damaged by `reason_code`) is a single query with a Postgres aggregate `FILTER` clause (`SUM(delta) FILTER (WHERE reason_code = 'damaged')`), not two separate queries or a GROUP BY on the column itself — `reason_code` takes other values too (or is null), so grouping by it doesn't cleanly bucket into "good vs damaged". `sql.join(ids.map(id => sql\`${id}\`), sql\`, \`)` (already used in `server/routes.ts`) is the established way to splice a dynamic `IN (...)` list into a raw `sql\`...\`` template in this codebase — reach for that instead of drizzle's `inArray()` the moment the query is already a raw `db.execute(sql\`...\`)` (mixing a raw template with a builder-only helper like `inArray` doesn't work; `inArray` is fine standalone in a normal `.where()` chain, which the PO list endpoint's own aggregate-by-`whPoLines.poId` query uses instead, since THAT one has no FILTER and stays fully in the query builder).
- 2026-07-22 (T6) — CRUD "can this be deleted/edited" guards that depend on ledger history (e.g. "can't delete a PO/PO-line once anything's been received against it") can't be expressed as a DB FK constraint here, because `wh_movements.ref_id` is a deliberately un-FK'd polymorphic int (D15's `ref_kind`/`ref_id` pattern has to point at completely different tables depending on `ref_kind`, which Postgres can't express as one real foreign key) — so the guard has to be an explicit pre-delete/pre-update query against `wh_movements` in the route handler itself, not something the database will ever reject on its own. Any future task deleting/editing a requisition, loan, or count that already has movements referencing it needs the same manual guard, not an FK-driven 23503 catch.
